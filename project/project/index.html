    1. Project Overview

    This project is a cloud-based application that simulates a text-to-911 emergency communication service. A user submits a simulated emergency text message through a web interface. The application sends the message to a backend API, validates it, stores it in a relational database, and displays it in an administrative dashboard for authorized reviewers.

    The application will also demonstrate a triage-assistance workflow. A Python service will evaluate message content using configurable keyword rules and, where available, an local large language model (LLM) served by Ollama. The resulting priority is a suggestion for a human reviewer, not a decision to dispatch emergency services. Reviewers can inspect the original message, see the rationale for a suggested priority, change the priority, and record their review.

    The project is intended for software-engineering education and demonstration. It will use synthetic messages and will not connect to a public-safety answering point (PSAP), emergency telephone network, SMS gateway, or live dispatch system. It is not designed or certified for operational emergency use.

    The implementation emphasizes a consistent, maintainable open-source stack:

    • Frontend: React and Vite.
    • Backend API: Python and FastAPI.
    • Database: MariaDB.
    • Data access and migrations: SQLAlchemy and Alembic.
    • Triage assistance: Python rules engine with Ollama local LLM analysis.
    • Deployment: Docker and Docker Compose.
    • CI/CD: GitHub Actions and GitHub Container Registry (GHCR).
    • Reverse proxy and HTTPS: Caddy.
    • Observability: Prometheus, Grafana, and Loki.

    2. Problem Statement

    Emergency communication environments may receive messages that vary in urgency, clarity, and completeness. In a real environment, staff need reliable processes for reviewing incoming communications, identifying potentially urgent situations, and maintaining an accurate record of actions taken.

    This project does not attempt to solve real-world emergency dispatch. Instead, it models a limited portion of the workflow so students can explore how a web application might receive, store, present, and organize simulated incoming messages. It also demonstrates the challenges of assisting human decision-makers with rule-based and language-model-based analysis.

    The project focuses on several software-engineering challenges:

    1. Accepting and validating messages through a web application.
    2. Persisting messages and their review history in a relational database.
    3. Applying transparent, testable rules to suggest priority levels.
    4. Presenting incoming messages in an administrative dashboard.
    5. Restricting access to administrative functions.
    6. Testing, deploying, monitoring, and documenting a containerized application.
    7. Communicating the limitations of automated classification and keeping a human reviewer in control.

    4. Minimum Viable Product (MVP) Scope

    The MVP will prioritize a complete end-to-end workflow over advanced integrations.

    In scope

    • React + Vite client interface for submitting synthetic messages.
    • FastAPI endpoints for creating and retrieving messages.
    • MariaDB storage using SQLAlchemy models and Alembic migrations.
    • Four-level priority suggestions using a deterministic Python keyword rules engine.
    • Optional Ollama analysis behind a configuration flag or mechanism; the application must still work when Ollama is unavailable.
    • Administrative dashboard for viewing, filtering, and reviewing messages.
    • Ability for a reviewer to override a suggested priority and record a reason.
    • Audit records for important message and review events.
    • Basic authentication and role-based authorization for administrative functionality.
    • Docker Compose configuration for local development and demonstration.
    • Automated tests and a documented CI workflow.
    • Synthetic seed data and a final demonstration script.

    Out of scope for the MVP

    • Connection to actual emergency services, PSAP systems, telephony, or dispatch software.
    • Sending real SMS messages or accepting live emergency communications.
    • Automatic dispatch or other consequential action based on model output.
    • Production-grade certification for public-safety use.
    • Advanced multi-region availability or disaster recovery.
    • A full production identity provider or enterprise single sign-on.
    • Unreviewed use of third-party AI services with message content.
    • Complex analytics, predictive modeling, or a public mobile application.

    Features such as live updates through WebSockets, external SMS gateways, advanced analytics, and expanded monitoring can be considered future work after the core workflow is stable.

    5. Technical Approach

    The system will use a modular architecture in which the frontend, API, database, triage logic, and supporting services have clearly defined responsibilities. Components will communicate through documented interfaces, and deployment configuration will be kept in version control without committing secrets.

    5.1 Cloud Architecture

    The application will be developed locally using Docker Compose and may be deployed to a small cloud virtual machine for demonstration. The exact hosting provider will be selected based on course requirements, available credits, and budget. Docker Compose is the deployment target for this proposal; the design does not assume AWS ECS or another managed container orchestrator.

    flowchart TD
    U[Client Browser] -->|HTTPS| C[Caddy Reverse Proxy]
    C --> F[React + Vite Frontend]
    C --> A[FastAPI Backend]
    A --> R[Python Priority Rules Engine]
    A -. optional analysis .-> O[Ollama Local LLM]
    A --> S[SQLAlchemy Data Access]
    S --> D[(MariaDB)]
    A --> L[Application Logs and Metrics]
    L --> P[Prometheus]
    L --> K[Loki]
    P --> G[Grafana]
    K --> G

    Component responsibilities

    • React + Vite: Provides the message submission interface and administrative dashboard.
    • Caddy: Acts as the public reverse proxy and handles HTTPS where the deployment environment supports a valid domain and certificate.
    • FastAPI: Exposes the application API, validates requests, applies authorization, coordinates triage analysis, and returns responses.
    • Python priority engine: Applies deterministic keyword rules and produces a suggested priority with reasons.
    • Ollama: Optionally hosts a local model for supplementary semantic analysis. Its output is untrusted input and must be validated.
    • SQLAlchemy: Maps application objects to relational database records.
    • Alembic: Tracks and applies schema migrations.
    • MariaDB: Stores messages, analysis results, reviewer actions, and audit history.
    • Prometheus, Grafana, and Loki: Provide metrics, dashboards, and log exploration when enabled.

    In development, services may be exposed only on the local machine. In a cloud deployment, only the required web entry point should be publicly reachable. MariaDB and Ollama should remain on an internal container network unless there is a specific, secured administrative requirement.

    5.2 Open-Source DevOps and Deployment Pipeline

    The pipeline will automate repeatable quality checks and container builds. A successful CI run does not by itself prove that a deployment is safe or operational; deployment verification remains a separate step.

    5.2.1 Source Control

    The project source code, application configuration templates, database migrations, tests, and deployment files will be maintained in a Git repository.

    Recommended repository organization:

    911-call-center-analysis/
├── frontend/
├── backend/
│   ├── app/
│   ├── tests/
│   ├── alembic/
│   └── alembic.ini
├── deployment/
│   ├── docker-compose.yml
│   └── Caddyfile
├── monitoring/
│   ├── prometheus/
│   └── grafana/
├── docs/
├── .github/
│   └── workflows/
├── .env.example
├── .gitignore
└── README.md

    The exact layout can be adjusted during implementation. The repository must exclude real .env files, credentials, database dumps containing sensitive data, and other secrets. Pull requests should be reviewed before merging to the main branch.

    5.2.2 Continuous Integration

    GitHub Actions will run automated checks when a pull request is opened or code is pushed. The workflow should include:

    1. Install the supported Python and Node.js versions.
    2. Install backend dependencies from the project's dependency files.
    3. Run backend formatting or lint checks.
    4. Run Python unit and API tests.
    5. Install frontend dependencies using the committed lockfile.
    6. Run frontend lint checks and production build.
    7. Start a disposable MariaDB service for integration tests where supported.
    8. Build application container images.
    9. Publish test results and logs when a step fails.

    CI should fail when a required test or build fails. The workflow should not publish release images from untrusted pull requests or expose deployment secrets to pull-request code.

    5.2.3 Database Testing

    Database tests will verify that SQLAlchemy models, Alembic migrations, and repository operations behave as expected.

    Tests should cover:

    • Creating and retrieving messages.
    • Validating required message fields.
    • Persisting suggested priority and analysis rationale.
    • Recording reviewer overrides and audit events.
    • Enforcing relationships between messages, analyses, and audit entries.
    • Applying migrations to a clean database.
    • Confirming that indexes and constraints exist as intended.

    Tests should use disposable test data and a dedicated test database. They must not connect to a production database or use real emergency records.

    5.2.4 Security Testing

    The CI pipeline should include dependency vulnerability checks and basic static checks where practical. The team should also review:

    • Whether secrets are absent from the repository.
    • Whether administrative endpoints require authentication and authorization.
    • Whether user-supplied text is validated and safely rendered.
    • Whether SQL is parameterized through the ORM or bound parameters.
    • Whether container images use supported base images and avoid unnecessary packages.
    • Whether error responses expose stack traces, secrets, or internal configuration.

    Automated checks supplement rather than replace a manual security review.

    5.2.5 Docker Build

    Each service will have a reproducible container build. Images should use pinned or deliberately maintained base-image versions, install only necessary dependencies, and avoid running as root where feasible.

    The frontend should be built for production and served through the selected web-serving configuration rather than relying on the Vite development server in production. The backend container should start the FastAPI application with a production-appropriate server configuration.

    5.2.6 Container Image Registry

    GitHub Container Registry (GHCR) will store versioned application images. The pipeline may publish images on merges to the main branch and create immutable release tags for approved versions.

    Images should be tagged with a commit SHA or release version. Deployment should use a known tag rather than an ambiguous latest tag wherever practical. Registry credentials must be stored as GitHub Actions secrets or equivalent protected credentials.

    5.2.7 Continuous Deployment

    Continuous deployment will be implemented only to the extent supported by the hosting environment and project schedule. A deployment job may connect to the target host using a restricted deployment credential, pull the selected images, and restart services using Docker Compose.

    The deployment process should:

    • Run only after required CI checks pass.
    • Use protected secrets and restricted permissions.
    • Avoid printing credentials in logs.
    • Preserve the prior working image tags for rollback.
    • Report success only after health checks and smoke tests pass.

    If automated deployment is not feasible for the course environment, the same documented commands can be run manually. This should be described accurately rather than represented as a fully automated deployment.

    5.2.8 Docker Compose Deployment

    Docker Compose will define the frontend, backend, MariaDB, and optional supporting services. Caddy and observability services can be included in a deployment profile so they do not consume unnecessary resources during basic local development.

    The Compose configuration should define:

    • A persistent volume for MariaDB data.
    • Internal networking between application services.
    • Health checks and service dependencies where appropriate.
    • Environment-variable configuration.
    • Restart policies appropriate to the environment.
    • Resource limits where supported and useful.
    • Separate development and demonstration settings when their requirements differ.

    The application should not depend on a developer's local machine paths or hard-coded credentials.

    5.2.9 Database Deployment

    MariaDB will run as a containerized service for the MVP. A persistent volume will protect database files across container recreation, but a volume alone is not a backup strategy. The team should document how to create and restore a database backup for demonstration purposes.

    Alembic migrations will be applied in a controlled deployment step before the new application version is considered ready. Migrations should be reviewed for compatibility and tested against a clean database. Destructive migrations require particular care because they may prevent rollback to an older application version.

    5.2.10 Ollama Deployment

    Ollama is an optional service for local LLM analysis. The application must remain usable if Ollama is disabled, a model is not downloaded, or the service is unavailable.

    If enabled:

    • The model should run locally in the same private environment where practical.
    • The selected model and required resources should be documented.
    • Model downloads should be performed deliberately because models can be large.
    • Requests should have timeouts and bounded input lengths.
    • Model output must be parsed and validated against a defined schema.
    • A model failure should fall back to the deterministic rules engine.
    • Model output must never trigger dispatch or another real-world action.

    Ollama's resource requirements may exceed those of the core MVP. If the host lacks sufficient memory or compute, the LLM component should be disabled and demonstrated separately.

    5.2.11 Monitoring

    Prometheus, Grafana, and Loki will provide an introductory observability stack when resources permit.

    • Prometheus: Collects application and infrastructure metrics, such as request counts, latency, error rates, and service availability.
    • Grafana: Displays metrics and, where configured, log-derived information in dashboards.
    • Loki: Aggregates application logs for troubleshooting.

    Logs must not include full message bodies, credentials, authentication tokens, or other sensitive data by default. Because the application uses synthetic messages, sample logs can be used for demonstrations, but the logging design should still follow data-minimization practices.

    5.2.12 Health Checks

    The API should expose a health endpoint that indicates whether the application process is running. A separate readiness check may verify whether essential dependencies, such as MariaDB, are reachable.

    Health endpoints should return only the information needed for monitoring and must not disclose credentials, internal network details, or stack traces. Ollama should be treated as optional; its absence should not make the core API unhealthy when LLM analysis is disabled.

    5.2.13 Deployment Verification

    After deployment, the team will run a smoke-test checklist:

    1. Confirm that containers start successfully.
    2. Confirm that the API health endpoint responds.
    3. Confirm that the frontend loads through the configured web entry point.
    4. Submit a known synthetic message.
    5. Verify that the message is stored in MariaDB.
    6. Confirm that the priority suggestion and explanation appear in the dashboard.
    7. Change the priority as an authorized reviewer and verify that the action is recorded.
    8. Confirm that logs and metrics are available when monitoring is enabled.
    9. Check application logs for unexpected errors.
    10. Confirm that no secrets or full message contents appear in ordinary logs.

    Deployment is considered verified only after the relevant checks have passed and the results are recorded.

    5.2.14 Rollback Strategy

    If a release fails its smoke tests, the team should restore the previously known-good application image tags and restart the services. Database changes must be considered separately: an application rollback may not be safe if the new release has already applied a destructive schema migration.

    The preferred approach is to use backward-compatible migrations where possible, retain a recent backup before risky schema changes, and document a restore procedure. A rollback should be tested in a non-production environment before it is relied upon.

    5.2.15 Complete Pipeline

    The intended workflow is:

    flowchart TD
    A[Developer creates branch] --> B[Open pull request]
    B --> C[Lint and automated tests]
    C --> D{Checks pass?}
    D -- No --> E[Fix issues and rerun checks]
    E --> C
    D -- Yes --> F[Review and merge]
    F --> G[Build container images]
    G --> H[Publish versioned images to GHCR]
    H --> I[Deploy with Docker Compose]
    I --> J[Run health checks and smoke tests]
    J --> K{Deployment verified?}
    K -- No --> L[Rollback and investigate]
    K -- Yes --> M[Record release and verification evidence]

    5.2.16 Definition of Done

    A feature or release is complete when:

    • Its acceptance criteria are met.
    • Relevant automated tests pass.
    • The frontend production build and backend checks pass.
    • Database migrations are reviewed and tested when applicable.
    • Authentication and authorization behavior has been checked.
    • Documentation and configuration examples are updated.
    • No secrets or real emergency data are committed.
    • The feature is demonstrated using synthetic data.
    • Deployment and rollback instructions are current when the feature affects deployment.
    • Any known limitations are documented rather than hidden.

    5.3 Architecture Component Description

    Frontend: React + Vite

    The frontend will contain two main user-facing areas:

    1. Client message submission: A simple form for entering synthetic message text and any other fields required by the scenario.
    2. Administrative dashboard: A protected interface for authorized reviewers to browse messages, filter by suggested priority and status, inspect analysis rationale, and record review actions.

    The frontend will call the FastAPI API over HTTP. It will not connect directly to MariaDB or Ollama. Client-side validation will improve usability, while the backend remains responsible for enforcing validation and authorization.

    Backend API: FastAPI

    FastAPI will provide endpoints for message creation, message retrieval, analysis, reviewer actions, and health checks. Request and response models will be explicitly defined, and errors will use predictable HTTP status codes and response structures.

    Example endpoint outline:

      -------------------------------------------------------------------------------
  Method                  Endpoint                        Purpose
  ----------------------- ------------------------------- -----------------------
  `POST`                  `/api/messages`                 Validate and store a
                                                          synthetic message, then
                                                          create a priority
                                                          suggestion.

  `GET`                   `/api/messages`                 Return a paginated list
                                                          for authorized
                                                          dashboard users.

  `GET`                   `/api/messages/{id}`            Return message details
                                                          and associated
                                                          analysis/review
                                                          history.

  `PATCH`                 `/api/messages/{id}/priority`   Record an authorized
                                                          reviewer's priority
                                                          override and reason.

  `POST`                  `/api/messages/{id}/review`     Record a review action
                                                          or note.

  `GET`                   `/health`                       Return process health.

  `GET`                   `/ready`                        Report readiness of
                                                          essential dependencies.
  -------------------------------------------------------------------------------

    This is a proposed contract; exact fields, pagination conventions, and response formats should be finalized before implementation. Administrative endpoints must enforce authorization on the server, not merely hide controls in the frontend.

    Data access: SQLAlchemy and Alembic

    SQLAlchemy will provide the database models and queries. Alembic will maintain versioned schema migrations. Database access should be isolated from API route handlers where practical, and transaction boundaries should ensure that a message and its associated audit event are not left in an inconsistent state.

    Triage assistance: Python and Ollama

    The Python rules engine will be the baseline classifier because its behavior can be tested and explained. Ollama can provide optional semantic analysis, but it must not replace the deterministic baseline or become a required dependency for core message submission.

    Database and monitoring

    MariaDB will be the system of record. Prometheus, Grafana, and Loki will be optional supporting services for metrics, dashboards, and logs. Docker Compose will make the services reproducible across developer machines and the demonstration host.

    5.3.1 MariaDB Database Schema

    The schema below is a starting point for the MVP. It should be implemented through SQLAlchemy models and Alembic migrations rather than maintained only as a manually executed SQL script. Field sizes, deletion behavior, and indexes should be confirmed during implementation.

    CREATE TABLE emergency_sessions (

    review_status ENUM('NEW', 'IN_REVIEW', 'REVIEWED', 'CLOSED')

);

    id BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
    message_id BIGINT UNSIGNED NOT NULL,

    suggested_priority ENUM('CRITICAL', 'HIGH', 'MODERATE', 'LOW')

    Schema notes

    • All records must contain synthetic data only.
    • The current_priority field represents the current value shown to the reviewer; suggested_priority preserves the initial system suggestion.
    • message_analysis allows multiple analysis attempts to be recorded over time.
    • message_audit_log records relevant events, including priority overrides and review-status changes.
    • The reviewer_reference and actor_reference fields are illustrative identifiers. If a users table is added, they should be replaced or supplemented with appropriate foreign keys.
    • A production-grade audit design would require stricter retention, access, and tamper-resistance controls than this educational schema provides.
    • JSON support and enum behavior should be verified against the selected MariaDB version and SQLAlchemy dialect.
    • The schema should be migrated and tested from a clean database in CI.

    5.3.2 Python Priority Ranking and Triage Engine

    The triage engine will provide a suggested priority for each submitted synthetic message. The first version will use deterministic rules that match configured phrases or keywords. Rules should be versioned and tested, and each suggestion should include a short explanation of the matches that influenced it.

    The four suggested levels are:

      -----------------------------------------------------------------------
  Priority                            Illustrative interpretation
  ----------------------------------- -----------------------------------
  **Critical**                        Text contains configured indicators
                                      of immediate, potentially
                                      life-threatening danger.

  **High**                            Text indicates a potentially
                                      serious or time-sensitive
                                      situation.

  **Moderate**                        Text describes a concern requiring
                                      review but contains no configured
                                      higher-priority indicator.

  **Low**                             Text appears non-urgent or
                                      informational under the configured
                                      demonstration rules.
  -----------------------------------------------------------------------

    These labels are illustrative, not validated emergency-dispatch categories. The project must not imply that the rules are clinically, operationally, or legally approved.

    A basic classification workflow:

    1. Normalize text for matching while preserving the original message.
    2. Evaluate configured high-priority and lower-priority rules.
    3. Record matched terms or rule identifiers.
    4. Select a suggested level according to documented precedence.
    5. Store the suggestion and explanation.
    6. Display the suggestion to the reviewer with a clear notice that it requires human review.

    Keyword matching has limitations. A word such as "breathing" may appear in a serious statement, a negated statement, or a hypothetical example. The test suite should include negation, misspellings, ambiguous phrases, multiple simultaneous indicators, and messages that do not match any configured rule. The system should prefer transparent uncertainty over claiming that a message has been understood reliably.

    Optional Ollama analysis

    If enabled, the application may send a bounded synthetic message to a locally hosted Ollama model and request structured output. The response should include a suggested level, concise rationale, and uncertainty indicator. The application must validate every field against an explicit schema, reject malformed output, and treat the model's explanation as untrusted generated content.

    The LLM must not be the sole authority for priority. If the rules engine and LLM disagree, the application should record the disagreement and make it visible to the reviewer. If Ollama times out or is unavailable, the rules-based workflow must continue. Model confidence values, if present, should not be treated as calibrated probabilities unless calibration has been tested.

    5.4 Security, Privacy, and Responsible Use

    Although this project is educational, it represents a sensitive domain and should model conservative security practices.

    • Authentication and authorization: Administrative pages and endpoints must require authentication. Server-side role checks must protect listing, reviewing, and priority-override actions.
    • Secret management: Credentials and signing keys must be supplied through environment variables or a secrets manager. .env files containing real secrets must not be committed. .env.example should contain placeholders only.
    • Transport security: Use HTTPS through Caddy when deployed with a valid domain and certificate. Local development may use localhost configuration.
    • Network isolation: MariaDB and Ollama should not be publicly exposed. Only required application ports should be reachable.
    • Input validation: Validate required fields, maximum message length, identifiers, and accepted enum values on the backend.
    • Database safety: Use SQLAlchemy or bound parameters, enforce appropriate constraints, and avoid returning raw database errors to clients.
    • Dependency and container security: Keep dependencies and base images maintained; run vulnerability checks where practical; use least-privilege container settings.
    • Auditability: Record reviewer overrides and important state changes without logging unnecessary personal information.
    • Data minimization: Use synthetic messages and avoid collecting names, phone numbers, precise addresses, or other real personal information.
    • LLM safety: Keep Ollama internal, limit input size, validate structured output, handle timeouts, and prevent model text from being interpreted as instructions or executable actions.
    • Human oversight: Every automated priority is advisory. No model or rule should trigger a dispatch action or contact emergency services.
    • Clear disclaimer: The interface, README, and demonstration should state that the application is a simulation and is not suitable for real emergency use.

    5.5 Multi-Environment Cloud Strategy: Multipass, Jetstream 2, and Google Cloud Platform

    5.5.1 Overview

    The 911 Call Center Analysis and Cloud-Based Emergency Triage System uses a multi-environment cloud strategy to support local development, cloud infrastructure testing, and deployment demonstrations. The project uses Multipass to create local Ubuntu virtual machines, Jetstream 2 to test virtual machine provisioning through OpenStack, and Google Cloud Platform (GCP) to demonstrate public-cloud deployment capabilities when resources and project requirements permit.

    The application follows a containerized architecture consisting of a React frontend, a FastAPI backend, and a MariaDB database. Docker and Docker Compose provide a consistent method for running the application across environments. The backend uses SQLAlchemy and Alembic for database access and schema migrations, while the triage component analyzes submitted messages and assigns preliminary priority levels based on predefined keywords. An optional local large language model (LLM), such as Ollama, supports additional message analysis without directly controlling emergency dispatch decisions.

    The system is an educational simulation. It uses synthetic emergency messages and does not connect to real 911 infrastructure or dispatch services.

    5.5.2 Local Development with Multipass

    Multipass provides lightweight Ubuntu virtual machines on the local development machine. These virtual machines create a Linux environment for testing application components and deployment configurations without requiring a separate physical server or public-cloud instance.

    Within the Multipass environment, the project runs Docker and Docker Compose to start the frontend, backend, and database services. Developers use this environment to verify application functionality, test API endpoints, apply database migrations, and examine communication between containers.

    Multipass also supports testing of configuration changes, database persistence, service startup, and recovery after individual containers stop or restart. The environment provides a repeatable testing setup that helps identify configuration and integration issues before the application runs on remote infrastructure.

    Resource-intensive components, including local LLM inference and the full monitoring stack, depend on the host machine's available CPU, memory, and storage. These components remain optional during local development so the core application can run within reasonable hardware constraints.

    5.5.3 OpenStack Infrastructure Testing with Jetstream 2

    Jetstream 2 provides cloud-based virtual machine infrastructure through OpenStack. The project uses this environment to explore cloud resource provisioning and verify the deployment process outside the local development machine.

    The workflow uses OpenStack credentials and configuration to authenticate with Jetstream 2, provision a virtual machine, configure network access, and connect through SSH. After the instance is available, the deployment environment installs or uses the required container tooling, retrieves the application's container images from the GitHub Container Registry (GHCR), and starts the services with Docker Compose.

    The project verifies that the application starts successfully, that the frontend can communicate with the backend, and that the backend can connect to MariaDB. Smoke tests and command-line checks help identify failures involving provisioning, authentication, networking, container startup, and application configuration.

    Security groups restrict network access to the ports required for administration and application traffic. Database access remains limited to the application environment rather than being exposed publicly. Credentials and other sensitive configuration values are supplied through environment-specific configuration instead of being stored in the source code.

    Jetstream 2 also provides an environment for examining infrastructure-related failures, including unavailable compute resources, incorrect credentials, and networking misconfiguration. Since cloud resource availability depends on the platform's current capacity and allocation policies, successful provisioning is recorded separately from successful application testing.

    5.5.4 Public-Cloud Deployment with Google Cloud Platform

    Google Cloud Platform provides a public-cloud environment for demonstrating how the containerized application operates outside the local and academic research cloud environments.

    The project uses a Compute Engine virtual machine as the primary deployment model for GCP. The VM runs the containerized application through Docker Compose, using the same application components and container images as the other environments. This approach limits environment-specific changes and keeps the deployment process consistent.

    Caddy provides HTTPS termination when the deployment configuration and domain or certificate arrangements support it. Network firewall rules restrict access to the necessary services, while SSH access and service credentials follow least-privilege practices. Application health checks and logs help verify service availability and troubleshoot deployment issues.

    The GCP environment also illustrates operational considerations associated with public-cloud hosting, including resource sizing, access control, external network exposure, and cost management. Compute resources are shut down or removed when they are no longer needed to avoid unnecessary charges.

    The project retains the option to discuss managed services such as Cloud SQL or container orchestration through Google Kubernetes Engine (GKE) as possible architectural extensions. These services are distinct from the core deployment and are not required to run the current application.

    5.5.5 Environment Usage Across the Project Lifecycle

    The three environments serve different purposes throughout the software development lifecycle.

    Project stage Environment Purpose

    Integration testing Multipass Verify communication between React, FastAPI, MariaDB, and supporting services.
    Infrastructure testing Jetstream 2 Practice OpenStack authentication, virtual machine provisioning, security group configuration, and SSH access.
    Remote deployment testing Jetstream 2 Run containerized services on a provisioned cloud VM and verify application connectivity.

    5.5.6 Configuration, CI/CD, and Observability

    The project uses Docker images and environment-specific configuration to maintain consistency across deployment environments. Application code and container definitions remain version-controlled, while environment variables hold settings that differ between local and remote deployments. Database schema changes are managed through Alembic migrations, allowing the database structure to be updated consistently.

    GitHub Actions supports continuous integration by running automated tests and other quality checks when configured events, such as pushes or pull requests, occur. The pipeline can also build and publish versioned container images to GHCR. Remote deployments use identifiable image versions so the running application can be traced to a specific build.

    The CI/CD pipeline verifies the checks included in its workflow, but a successful build does not by itself prove that a remote deployment is healthy. Application startup, database connectivity, network access, and endpoint availability are checked separately in the target environment.

    Prometheus, Grafana, and Loki provide the project's observability architecture for collecting metrics, visualizing system behavior, and examining logs when these components are enabled. Together with application health checks, these tools support troubleshooting across the frontend, backend, database, and deployment infrastructure. Their resource requirements are considered when deciding which components run in each environment.

    5.5.7 Security, Cost, and Environment Validation

    Security and cost management are considered throughout the deployment workflow. The project avoids committing secrets to version control, restricts access to administrative and database services, and uses environment-specific settings to separate local testing from remote deployments. Synthetic data is used throughout the educational simulation, and the application does not process real emergency dispatch traffic.

    Local development through Multipass limits reliance on paid cloud infrastructure. Jetstream 2 supports cloud infrastructure experimentation subject to account permissions and available resources, while GCP provides a separate public-cloud environment with its own usage costs and access requirements. Remote resources are monitored and removed when no longer needed.

    Environment validation records the results of application tests and infrastructure operations separately. The project documents which environments successfully run the application, which provisioning and deployment steps pass, and which operations remain limited by configuration, permissions, available resources, or project scope.

    The multi-environment approach demonstrates how a single containerized application can move from local development to cloud infrastructure testing and public-cloud deployment while maintaining consistent application components, controlled configuration, repeatable deployment steps, and clear verification procedures.

    5.5.8 Infrastructure Provisioning with Cloudmesh cmx vm

    The project integrates the Cloudmesh cmx vm command-line interface to support virtual machine management and infrastructure automation. Cloudmesh provides a command-line interface for interacting with configured cloud providers, allowing infrastructure operations to be performed and tested through repeatable commands rather than relying exclusively on a cloud provider's web interface.

    Within the project's multi-environment strategy, cmx vm supports the cloud infrastructure workflow by helping manage virtual machine providers, initiate VM provisioning, and inspect available instances. It complements Docker and Docker Compose, which manage the application's containerized services after the underlying virtual machine is available.

    Role in the project

    The cmx vm workflow supports the following activities:

    • Provider configuration: Inspect configured cloud providers and select the provider used for infrastructure testing.
    • Virtual machine provisioning: Submit commands to create a virtual machine using the selected provider's configuration and available resources.
    • Instance inspection: List virtual machines and inspect command results to determine whether an instance is available.
    • Infrastructure testing: Run repeatable command-line tests that record which VM operations succeed, fail, or are skipped because of environmental constraints.
    • Deployment preparation: Use a successfully provisioned and accessible VM as the target for installing or running Docker and Docker Compose.
    • Troubleshooting: Capture command output and error messages to investigate authentication problems, missing configuration, key-pair mismatches, resource limits, and provisioning failures.

    Integration with Jetstream 2 and other environments

    Jetstream 2 provides the cloud infrastructure environment for OpenStack-related testing when the appropriate provider configuration, credentials, and resources are available. The project uses cmx vm for supported provider operations and records the outcomes of those operations as part of its infrastructure testing.

    Multipass remains the local virtual machine environment for development and integration testing. GCP remains the optional public-cloud deployment environment and uses its own supported provisioning and access mechanisms unless a compatible Cloudmesh integration is explicitly configured and tested. The project does not assume that cmx vm manages every environment through the same commands.

    Testing and verification

    The project uses Python tests with pytest to exercise selected cmx vm command-line operations. The tests invoke commands through a command runner, capture exit codes and output, and record whether each operation passes, fails, or is skipped. This approach makes the infrastructure workflow reproducible and helps distinguish a command-line failure from an application deployment failure.

    The tests cover applicable operations such as:

    • Listing configured VM providers.
    • Selecting the configured provider.
    • Starting a test VM.
    • Listing virtual machines after a provisioning attempt.
    • Recording errors when authentication, configuration, key-pair validation, or resource availability prevents an operation from completing.

    Tests that create cloud resources are designed to account for external dependencies. A failed provisioning attempt is recorded as a failure or an environment-dependent skip according to the test's defined criteria; it is not treated as evidence of successful deployment.

    Relationship to the application deployment pipeline

    The cmx vm workflow and the Docker Compose workflow have separate responsibilities:

    1. Cloudmesh commands manage supported cloud infrastructure operations.
    2. The cloud provider supplies the virtual machine and its network resources.
    3. The deployment process prepares the VM and starts the application's containers.
    4. Smoke tests verify application health, frontend-to-backend communication, and database connectivity.
    5. Test output and deployment evidence are recorded in the project documentation.

    This separation allows the project to evaluate infrastructure automation independently from application functionality. A successful cmx vm command does not, by itself, demonstrate that the application is deployed or operational. Application-level verification remains a separate requirement.

    Integrating cmx vm therefore extends the project's cloud computing and DevOps coverage by combining command-line infrastructure management, automated testing, failure reporting, and containerized application deployment.

    6. Development Features

    6.1 Working Message System

    A user will enter a synthetic emergency message in the React interface and submit it to the FastAPI backend. The backend will validate the request, save the message in MariaDB through SQLAlchemy, and create an initial priority analysis. The API will return a message identifier and the resulting status.

    Acceptance criteria:

    • Required fields are validated on the server.
    • Invalid submissions return a clear error response.
    • Valid submissions are stored and can be retrieved.
    • The submitted message appears in the administrative dashboard.
    • The message and its analysis can be traced through a stable identifier.
    • All demonstration messages are synthetic.

    6.2 Automated Prioritization

    The MVP will use the Python keyword rules engine to assign one of four suggested priority levels: Critical, High, Moderate, or Low. Each result should include an explanation or matched rule identifiers. Ollama semantic analysis is optional and should be introduced only after the baseline workflow and tests work.

    Acceptance criteria:

    • The rules engine returns a valid priority for supported inputs.
    • The explanation records the rules or indicators that were matched.
    • The four-level vocabulary is used consistently in the API, database, and interface.
    • Ambiguous, negated, and conflicting indicators are covered by tests.
    • Failure of optional LLM analysis does not prevent message submission or review.
    • The interface identifies results as suggestions requiring human review.

    6.3 Functional Call Center Dashboard

    The dashboard will provide a single place for an authorized reviewer to inspect simulated incoming messages. It will show message submission time, current and suggested priority, review status, and the explanation available from the triage engine.

    Core functionality:

    • List and inspect messages.
    • Filter by priority and review status.
    • Sort by submission time or priority.
    • View analysis details and audit history.
    • Override the current priority with a recorded reason.
    • Update the review status.
    • Clearly distinguish the original system suggestion from the reviewer's current decision.

    The dashboard must not imply that an item has been dispatched, that an actual emergency service has received it, or that a priority suggestion is authoritative.

    6.4 Cloud Deployment

    The application will be containerized and run through Docker Compose. The demonstration environment may use a small cloud VM if one is available within the budget. Caddy may serve as the HTTPS reverse proxy, while MariaDB remains on a private network. The optional monitoring stack will be enabled only when the host has adequate resources.

    Acceptance criteria:

    • A new environment can be configured from documented steps.
    • Required variables are documented in .env.example.
    • Services start through the documented Compose command.
    • Persistent database storage is configured.
    • Health checks and a smoke test are documented.
    • Secrets are not embedded in images or committed to the repository.

    10. Database Selection: PostgreSQL vs. MariaDB

    The application requires a relational database for messages, analysis results, review states, and audit history. PostgreSQL and MariaDB are both mature open-source relational database systems that can support this type of application. The project will use MariaDB for consistency with the selected implementation plan, while retaining PostgreSQL as a considered alternative.

    10.1 Database Selection Criteria

    The database choice should consider:

    • Reliability and transaction support.
    • Compatibility with Python and SQLAlchemy.
    • Migration support through Alembic.
    • Ease of local development and Docker deployment.
    • Availability on the selected hosting environment.
    • Familiarity for the project team.
    • Documentation and community support.
    • Backup, restore, and monitoring options.
    • Resource requirements and expected project scale.
    • The complexity of the data model and queries.

    For the MVP, both candidates meet the main functional requirements. The selection is therefore primarily a project consistency and implementation decision, not a claim that one database is universally superior.

    10.2 Why PostgreSQL Was Considered

    PostgreSQL is a strong open-source relational database with robust transaction support, advanced SQL capabilities, extensive indexing options, and a mature ecosystem. It works well with Python applications and SQLAlchemy and could support the message, analysis, and audit tables required by this project.

    PostgreSQL would be a reasonable choice if the team had already standardized on it, needed a PostgreSQL-specific feature, or had an existing deployment environment built around it. It remains a viable alternative if implementation constraints change.

    10.3 Why MariaDB Is Appropriate for This Project

    MariaDB is a mature open-source relational database that supports the relational tables, constraints, indexes, and transactions required by the MVP. It can be run in Docker Compose and accessed from FastAPI through SQLAlchemy.

    MariaDB is appropriate for this project because:

    • It satisfies the application's current relational-data requirements.
    • It can be deployed consistently with the rest of the containerized stack.
    • SQLAlchemy and Alembic can support the application's data-access and migration workflow.
    • It provides a practical environment for demonstrating database schema design, persistence, indexing, and migration testing.
    • It avoids introducing multiple database options into a small MVP without a demonstrated need.

    These reasons are based on the project's scope. They do not imply that MariaDB is categorically better than PostgreSQL.

    10.4 MariaDB's Role in the Overall Architecture

    MariaDB will serve as the system of record for:

    • Synthetic emergency messages.
    • Suggested and current priority values.
    • Analysis results and explanations.
    • Review status and reviewer references.
    • Audit events for important state changes.
    • Optional session or scenario metadata.

    FastAPI will be the only application component that directly accesses the database. The React frontend will communicate with FastAPI and will never connect directly to MariaDB. SQLAlchemy will handle data access, and Alembic will track schema changes.

    Indexes will support common dashboard queries, especially sorting by submission time and filtering by priority and review status. The database will run on an internal network and should not be exposed directly to the public internet.

    10.5 Limitations and Tradeoffs

    The selected database does not remove the need for sound data modeling, migration discipline, access control, backups, or performance testing. Some features and data types differ between MariaDB and PostgreSQL, so database-specific SQL should be minimized unless there is a clear reason to use it.

    The team should verify behavior against the selected MariaDB version, particularly for JSON fields, enum handling, timestamp behavior, and SQLAlchemy dialect support. A future move to PostgreSQL would require compatibility testing and possibly schema or migration changes.

    For this educational project, operational complexity and implementation consistency matter more than advanced database features that the MVP does not need.

    10.6 Final Database Decision

    Decision: Use MariaDB for the MVP.

    MariaDB will be the only supported database target in the initial implementation. SQLAlchemy will provide data access and Alembic will manage migrations. PostgreSQL remains a technically viable alternative but will not be maintained as a parallel target unless a concrete requirement justifies the additional work.

    This decision keeps the deployment and testing plan focused while meeting the project's current persistence needs.
